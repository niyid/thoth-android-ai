A Security Walkthrough of the XMRWallet Fork
📅 May 2026 · ✍ Oyeniyi Dada · 🔗 github.com/niyid/xmrwallet · ⏱ 15 min read

A Bitcoin exchange's May 2026 exploit is the unlikely starting point for this piece — not because XMRWallet had anything to do with it, but because it's a clean reminder of where wallet software actually breaks. From there, a close read of every changed line between XMRWallet's upstream codebase and its niyid fork, and an argument that the same class of bug that hit Bisq may still be sitting, unaudited, inside Haveno.

§ A — Context

A Bitcoin Exchange's Bug, and Why Monero Should Care

On May 1, 2026, Bisq — the peer-to-peer Bitcoin trading platform built around censorship-resistance and self-custody — disclosed that an attacker had found a way to drain a slice of the offers sitting on its order book. The window was narrow, roughly twelve hours, and the damage was contained to offers the attacker actually managed to take: about 11 BTC in confirmed losses. Because Bisq holds no funds centrally, wallets that weren't mid-trade were never at risk.

The team's stopgap fix was almost comically blunt: they pointed the minimum required trading version at 2.0.0, a release number that doesn't exist, which had the effect of locking out every v1 client and stopping the bleeding. Bisq 2 — a separate codebase running the newer Bisq Easy protocol — was never in scope.

📋
What Bisq said happened

A missing validation check in the trade protocol let a modified client through. Anyone with a trade open on or after the morning of May 1 was told to select it and press Ctrl+O to start mediation.

The aftermath followed a predictable shape: containment first, then a shift toward hotfixes and a reimbursement conversation. Existing trades kept working, mediation and arbitration stayed online. But because Bisq runs as a DAO, any payout plan has to clear community governance first — there's no team with a checkbook who can simply make affected users whole. Treasury size and consensus decide the timeline, not urgency.

The Same Story, Six Years Earlier

Anyone who's followed Bisq for a while will recognize the shape of this immediately. In April 2020, the software failed to check that a trade's payout address actually matched Bisq's own donation address before it signed and broadcast a time-locked payout. A dishonest seller just had to wait out the clock — buyer funds, security deposit, and all, redirected straight to the attacker. Seven victims, roughly 3 BTC and 4,000 XMR, about a quarter million dollars at the time, all on the XMR/BTC pair.

In plain words, this exploit was the result of a flaw in the way Bisq trades are carried out, not in the way funds are stored.

— Bisq Network, April 2020 Security Statement

Neither incident, six years apart, involved broken cryptography. Both came down to a validation check that should have existed and didn't. That's the thread this piece pulls on — because it turns out to be exactly the right lens for reading a diff between two versions of a Monero wallet, too.

§ B — Background

Two Languages, One Wallet

XMRWallet — most people know it as Monerujo — is the Android wallet most Monero users reach for first: non-custodial, mobile-native, talking to the network directly through remote nodes. Under the hood it's really two applications stitched together:

  • A Java/Kotlin layer that owns everything the user actually sees — UI, wallet lifecycle, node selection, transaction history, preferences.
  • A native C++ layer that wraps Monero's own reference wallet library (wallet2_api.h) through JNI, handling the cryptography, transaction construction, and key material.

That split isn't a design choice so much as a fact of life — Monero's reference implementation is C++, full stop. But the seam where Java meets C++ is one of the more dangerous places in any Android codebase. Two memory models, two exception systems, and a thread boundary all meet at once, and the failure modes range from an ordinary crash to something much quieter: data that's silently wrong.

§ C — Framing

Where AI Actually Earns Its Keep in Codebases Like This

"AI-assisted development" covers a lot of ground, but in a project like XMRWallet it tends to show up in a handful of concrete, recognizable ways:

Scale

Repetitive hardening

Applying one safety pattern consistently across dozens of call sites in a large C++ file — exactly the kind of exhaustive work human reviewers tend to tire of halfway through.

Idiom

RAII generation

Producing resource-management wrappers that lean on the type system itself to enforce cleanup, rather than trusting every call site to remember.

Concurrency

Thread-safety review

Spotting shared mutable state and proposing mutex-guarded access around it.

Onboarding

Build tooling & docs

Lowering the friction to reproduce a build — which, in a supply-chain sense, is itself a security property.

The niyid fork of XMRWallet reads like a specimen of exactly this pattern: uniform application of a hardening idiom across a big file, consistent defensive checks, and a documentation set with a completeness that's hard to sustain through manual effort alone. What follows is a section-by-section read of what actually changed.

1. String Handling — from a Footgun to an RAII Guard

The upstream pattern for pulling a Java string across the JNI boundary is the textbook one, and it's fragile in a textbook way:

monerujo.cpp — upstream patternC++
const char *_password = env->GetStringUTFChars(password, nullptr); // ... use _password ... env->ReleaseStringUTFChars(password, _password);

Throw an exception, or hit an early return, anywhere between those two lines, and the string is never released — a leak. Worse, if GetStringUTFChars itself fails because an exception is already pending, the code keeps going with a null pointer nobody checked. In a wallet handling key material, a crash at exactly the wrong moment risks leaving things in a half-initialised state.

The fork replaces every instance of this with a small RAII class:

monerujo.cpp — fork's JNIStringGuardC++
class JNIStringGuard { JNIEnv* env; jstring jstr; const char* cstr; bool released; public: JNIStringGuard(JNIEnv* e, jstring s) : env(e), jstr(s), cstr(nullptr), released(false) { if (s != nullptr && env != nullptr) { try { cstr = env->GetStringUTFChars(s, nullptr); } catch (...) { LOGE("EXCEPTION in GetStringUTFChars"); cstr = nullptr; } } } ~JNIStringGuard() { if (cstr && env) env->ReleaseStringUTFChars(jstr, cstr); } const char* get() const { return cstr; } bool isValid() const { return cstr != nullptr; } JNIStringGuard(const JNIStringGuard&) = delete; JNIStringGuard& operator=(const JNIStringGuard&) = delete; };

The destructor releases the string no matter how the enclosing scope exits. isValid() makes the failure path explicit instead of implicit. Deleting the copy constructor rules out a double-release. And the constructor itself now catches the exception that the old pattern would have let escape unhandled. This is a genuine, substantive fix — not a stylistic one.

2. Null Guards, Everywhere

Every JNI entry point in the fork now opens with an explicit check:

monerujo.cpp — entry-point guardC++
if (path == nullptr || password == nullptr || language == nullptr) { LOGE("createWalletJ: null parameter(s) received"); return 0; }

Counting these across the file — 331 in the fork against 98 upstream, a 238% increase — it's fair to say the entry surface has been hardened systematically rather than opportunistically. A null JNI string slipping past a check like this can mean a segfault, a corrupted wallet, or in the worst case a write to memory an attacker had some say over. Closing that gap consistently, rather than case-by-case, is exactly the sort of work AI tooling is well suited to.

3. Threading: Three Mutexes Instead of One

Both versions protect the WalletListener callback with a _listenerMutex. The fork adds two more: a g_walletMutex guarding wallet creation and access, and a g_walletTrackerMutex protecting a global map that records every live wallet pointer and its creation context —

monerujo.cpp — lifecycle trackerC++
static std::unordered_map<Monero::Wallet*, std::string> g_walletTracker; static std::mutex g_walletTrackerMutex;

— which doubles as a leak-detection aid during development. The extra g_walletMutex matters in practice: a mobile app has background sync threads and UI-triggered operations interleaving constantly, and that's exactly where races creep in unnoticed.

4. Everything Else in the JNI Layer

A handful of smaller changes round out the file. Two JNI class references — class_ArrayList and class_WalletListener — lost their static qualifier, which widens their linkage from file-private to visible across the process; that's most likely an unintended side effect of a refactor rather than a deliberate choice, and worth flagging even though the practical exposure is narrow. A class_CoinsInfo reference and its two supporting functions were removed from the native side, but the Java CoinsInfo class itself is still there — untouched — meaning any caller that still expects the native bridge to support coin-control data will hit a null reference. And the Sidekick hardware-companion integration, previously a real confirmation gate requiring a physical tap before a transfer proceeds, is now stubbed to auto-confirm:

monerujo.cpp — ConfirmTransfers()C++
// upstream — real Sidekick round-trip bool ConfirmTransfers(const char *transfers) { JNIEnv *jenv = attachJVM(); jstring _transfers = jenv->NewStringUTF(transfers); jmethodID confirmMethod = jenv->GetStaticMethodID(class_SidekickService, "ConfirmTransfers", "(Ljava/lang/String;)Z"); return jenv->CallStaticBooleanMethod(class_SidekickService, confirmMethod, _transfers); } // fork — stubbed to always confirm bool ConfirmTransfers(const char *transfers) { LOGD("ConfirmTransfers: auto-confirming (Sidekick disabled)"); return true; }

That's a documented, deliberate decision — there's a remove_sidekick.sh script that spells out exactly what it does — for environments that don't have the Sidekick hardware available. It's the right call for that context, but it's worth repeating clearly: anyone relying on Sidekick as a second confirmation factor loses that protection silently if they deploy this fork without knowing.

On the tidier side of the ledger: the WalletListener struct became a proper class with explicit public/private sections, protecting its internal jlistener reference from accidental external access. A complete JNI_OnUnload was added, cleaning up every global reference the file holds rather than leaking them at library teardown. Three stray double-semicolons were fixed. And a full set of forward declarations was added at the top of the file, so the compiler catches mismatched signatures at the declaration rather than the call site.

§ E — The Rest of the Diff

Java, Build Scripts, and the Boring-But-Important Stuff

One Word, One Regression

The Java-layer diff is almost entirely one change:

TransactionHistory.java — line 71Java
// m2049r (upstream) private void refresh() { ... } // niyid (fork) public void refresh() { ... }

Upstream, refresh() is only ever reached through refreshWithNotes(), which repopulates the transaction list and then loads the user's private notes. Making it public opens a path that skips the notes entirely — any caller that takes it will render a transaction list stripped of its annotations, with no indication anything is missing. There may be a good reason (skipping notes during a bulk sync, say), but with no Javadoc explaining the invariant and no new caller in the fork actually using the wider visibility, it reads as an accidental side effect of a refactor that changed an access modifier just to get something to compile.

Build System: Paths, Pins, and Housekeeping

CMake changes twice: include_directories() now runs before add_library(), the more conventional order, and the external library layout moved from a flat per-ABI structure to a normalised output/<abi>/lib/ tree. That second change is a clean break — prebuilt libraries built for one codebase won't satisfy the other's paths anymore.

The Dockerfiles tell a small supply-chain story of their own. Upstream pins to debian:stable, a rolling tag that can silently resolve to a different Debian release depending on the day you build — the fork pins explicitly to debian:bullseye across all three architecture images, arm32, arm64, and a new x86_64 image for emulator testing. Pinned base images are the more defensible choice for anything security-sensitive, at the cost of needing a manual bump when Bullseye reaches end of life.

The .gitignore grew from 16 lines to 91, adding rules for *.a and *.so among other things — which matters more than it sounds like, since binary blobs committed to a repo can't be meaningfully reviewed and are a real supply chain risk on their own.

Set against that, four things need attention before this is production-ready:

  • Debug logging in release builds. The LOGD calls scattered through JNIStringGuard and the rest of the JNI layer need to be compiled out of release — logcat is readable by other apps with READ_LOGS on older API levels.
  • Public refresh() with no documentation. Either add the Javadoc explaining the invariant, or revert it. Undocumented, it's just an encapsulation risk.
  • The wallet tracker's runtime overhead. g_walletTracker and its mutex add cost to every wallet creation and teardown — this belongs behind a preprocessor flag, compiled out of release.
  • Verification of the extern "C" restructuring — likely fine, but worth confirming all JNI symbol exports still resolve correctly across every ABI.

Weigh it all together and the fork is technically ahead on code quality and security architecture, especially at the JNI boundary where the real risk concentrates. What it doesn't have — and can't manufacture — is the upstream's years of production exposure on real mainnet wallets. Best path forward: upstream the JNI hardening selectively, keep Sidekick support and CoinsInfo intact, and get the combined result.

§ G — The Tell

Is This Actually AI-Assisted? The Signs Say Yes

Nothing here is a smoking gun on its own, but the combination is hard to explain any other way:

  • Pattern consistency at scale. JNIStringGuard shows up at every relevant call site, dozens of them, with no drift in how it's applied. That kind of uniformity across a large file is unusual without tooling doing the heavy lifting.
  • Documentation with LLM-shaped completeness. Four separate docs — build instructions, a checklist, a quick start, a contributor table — each covering its slice thoroughly. That's a very particular kind of thorough.
  • Null checks with no gaps. Exhaustive coverage at every JNI entry point is exactly where manual review usually leaves holes, and exactly where an AI assistant doesn't get bored halfway through.
  • An RAII class written by someone (or something) that knows the idioms. Non-copyable semantics, an exception handler in the constructor, an explicit validity flag — all the marks of someone who's absorbed a lot of idiomatic C++.

None of that makes AI a substitute for review — it's a force multiplier, letting a small team apply best practices at a speed manual effort alone wouldn't sustain. And the flip side is right there in the same diff: the debug logging left in production paths, the quiet visibility change on refresh(), the tracker overhead nobody gated behind a flag. These aren't C++ knowledge gaps. They're deployment-context gaps — exactly what a human reviewer with production experience is for.

§ H — The Part Nobody's Talking About

If Bisq Had This Bug, Does Haveno Too?

Here's the question that doesn't seem to be getting asked publicly: if the May 2026 flaw lived in Bisq v1's trade protocol, what are the odds the same flaw exists in Haveno — and by extension in RetoSwap, which forks Haveno?

The lineage isn't a loose analogy. Haveno is a direct fork of Bisq, built by the Monero community specifically to swap Bitcoin for Monero as the base trading currency. RetoSwap forks Haveno in turn, and currently runs the only live Haveno network doing real trades. Haveno kept Bisq's Java application code, its P2P networking layer, and its dispute resolution architecture, adapting only the trade protocol logic for Monero's multisignature scheme. Any protocol-level bug in how Bisq v1 validates trade messages, offer parameters, or payout conditions is a candidate to exist verbatim in Haveno — unless that exact code path was deliberately rewritten during the fork.

Where the Two Actually Diverge

The biggest architectural split is the multisig model. Bisq moved to 2-of-2 (just buyer and seller, no arbitrator key) back in v1.2, a deliberate trust-minimisation step. Haveno went the other way on purpose, keeping the older 2-of-3 scheme with a live arbitrator key — because Monero has no native timelock and no chained-transaction mechanism, which makes Bisq v1's time-locked payout approach unworkable for XMR.

Protocol
Multisig Model
Bisq v1 (current)
2-of-2, buyer + seller only. Deadlocks resolve via time-locked payout to a DAO donation address.
Haveno / RetoSwap
2-of-3, buyer + seller + arbitrator, who can co-sign a payout with either party to resolve a dispute.

That difference is real, but it doesn't obviously insulate Haveno from this specific class of bug. The May 2026 exploit came down to a missing validation check on incoming trade messages — that kind of gap doesn't care whether the multisig underneath is 2-of-2 or 2-of-3. It depends entirely on whether the receiving peer validates a message's parameters before acting on it. If anything, Haveno's live arbitrator key arguably widens the blast radius: a validation bypass that lets a malicious client manipulate payout conditions could potentially pull an arbitrator's key into an unauthorised release — a scenario that's structurally impossible in Bisq v1's keyless model.

This isn't a hypothetical concern pulled from nowhere, either. In 2021, Haveno's own team found and responsibly disclosed a Bisq vulnerability that let attackers harvest payment details — bank account numbers, names, addresses — at essentially no cost. Bisq patched it in v1.7.0. The fact that Haveno's team caught that bug tells you they'd studied Bisq's codebase closely — and the same logic runs in both directions: code Haveno forked from Bisq inherited whatever bugs were already sitting in it at the time.

⚠
Where this leaves users

Until Haveno's team explicitly confirms they've audited this specific validation gap and ruled it out, treating Haveno and RetoSwap as potentially exposed is the sensible, conservative position — especially given how much harder stolen XMR is to trace or recover compared to BTC.

§ I — Takeaways

What This Means for AI-Assisted Wallet Engineering

  • AI shines at systematic refactors. JNIStringGuard is the ideal use case — applying one well-understood pattern consistently across a large, repetitive file. Doing that by hand across 30+ JNI functions is tedious enough that it rarely gets prioritised in a volunteer project.
  • It still needs a human in the loop. The refresh() visibility change and the production debug logging are exactly the subtle, context-dependent issues that need domain expertise to catch — AI tooling doesn't know your deployment the way your team does.
  • Documentation is a genuinely high-leverage use case. Better build infrastructure lowers the barrier to contribution and improves reproducibility — both real security properties, not just developer-experience niceties.
  • Validation logic is where wallets and trading protocols actually fail. Not cryptography — a missing payout-address check in 2020, a missing trade-validation check in 2026. Tools that can trace control flow and flag missing validation branches have direct, practical security value here.
  • The JNI boundary deserves disproportionate investment. Any project wrapping a C++ crypto library in Java via JNI inherits two memory models, two exception systems, and cross-language threading all at once. Time spent hardening that seam pays back more than its share.
⌗ Conclusion

Where This Leaves Us

XMRWallet sits at an intersection that raises the stakes on all of this: privacy-sensitive software, a genuinely complex dual-language architecture, maintained by volunteers, and used by people for whom operational security isn't an abstraction. Bisq's exploits in 2020 and 2026 are a standing reminder that missing validation or incomplete hardening in this space costs real funds belonging to real people.

The Haveno question makes that sharper still. Bisq for BTC pairs, Haveno and RetoSwap for XMR-native trading — the Monero ecosystem's P2P trading infrastructure shares a common ancestor, and a protocol-level bug found in one is a live candidate to exist in the others. The same privacy properties that make these platforms worth using are the ones that make recovering funds after an exploit nearly impossible, which raises the cost of getting the validation logic wrong.

What the niyid fork demonstrates, at minimum, is what intentional AI-assisted development can look like in practice: consistent pattern application, thorough build documentation, and meaningfully better defensive programming, produced at a pace that's hard to match by hand. It won't write a perfectly secure wallet on its own. But it can help a small, capable team do noticeably better work — and in an ecosystem built around privacy and security, better work translates directly into safer outcomes for the people using it. Whether that same rigor gets applied to trade-protocol validation before the next exploit, rather than after, is still an open question.
